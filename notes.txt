
Part 1
Refactoring:

1. Change 2D Array to map
    a. Change number[] to string.
    b. Decide String format.
    c. Add validations on string format during input from user.
2. Change all 2D array dependency to map.

Decide String format:
Usecase:
    1. While loop to iterate 2d array and check for pieces.
    2. Checks - need to verify if king is attacked by any enemy piece (P/K/B/R/Q).
    3. Pins - need to verify if piece is pinned to ally king by any enemy piece (B/R/Q).
    4. Captures - need to verify if square being attacked by ally piece has an enemey piece(P/K/B/R/Q) that can be captured. If enemy piece is the enemy king then it is a check and capture is not possible.
        a. En-passant - If enemy pawn is on same row as ally pawn and enemy pawn has moved 2 steps as it's first move and is the last move played by opponent, it can be captured.
    5. Promotions - need to verify if the square that is being attacked or advanced to by ally pawn is at the end of the board, for promotion.
    6. Castling - Check if the sqaures between the ally king and rook is empty(not occupied by ally pieces) and is not attacked from a distance by enemy pieces(P/K/B/R/Q/A).
    7. Draws - Either by 3 move repetition or by 50 move rule(no pawns have advanced and no capture in last 50 moves) or if there are insufficient pieces on board.
    8. Checkmate - Enemy king cannot move and is attacked, there is no enemy piece that can be sacrificed/captured to stop the checkmate.

Solution:
    1. Use index based string - '00' etc.
    2. Use piece id based strings - 'WP1'
        W - color (W - white, B - black)
        P - pieceType (P - pawn, K - knight, B - bishop, R - rook, Q - queen, A - king)
        1 - number of piece ( pawn(0-7), queen(0-8), bishop/knight/rook(0-9), king(NA))
        WP1 - a white pawn at position [1,1] or '11'

Advantages:
Solution 1: 
    1. FE can send index based position as a string, no need for FE to create complex map keys.
    2. Existing logic using while loops etc does not have to be changed, minimal changes would be required.

Solution 2:
    1. BE logic can efficiently use map to check for checks, pins, captures, promotions etc.

Disadvantages:
Solution 1:
    1. Not an effective way to use the map. Why loop over each position, when each individual piece can be directly checked. (ex: Check if enemy rooks are on same row or column, rather than looping over each square till the end of the board.)

Solution 2:
    1. Requires extensive code changes.

Part 2

Websocket implementations.

About websockets:
    Websockets are a relatively new technology enabling bi-direction communication between client and server over a single shared connection.

Advantages:
    - Low latency between client/server due to single connection.
    - Encryption using wss
    - Max message size is 100Mb.

Disadvantages:
    - No inbuilt security features.
    - No rate limiting.
    - No way to prevent DDos, as messages are sent over the same connection the servers buffer gets full, leading to out of memory errors.
    - Is relatively new and thus unsupported in some cases, like users behind corporate VPN's/firewalls. Leading to usage of long-polling(HTTP) as a fallback.

Implementing a vanilla websocket
    Client - Front end, player 1 and player 2.
    Server - Backend Chess Engine.

    - Rooms must be created, to handle chess game between 2 live players.
    - Use wss, to encrypt messages from client.
    - Verifying client and server messages. 
        Server can verify client messages by verifying origin header. Server can additionally verify using HMAC
        Client can verify server messages using HMAC verification, ask chatgpt Sign Server Messages with HMAC (Tamper Detection).
        worst case: implement encryption on both client and server
    - Rate limiting must be implemented (check link for possible implementation: https://github.com/uNetworking/uWebSockets.js/issues/335#issuecomment-834141711)
    - Clocks must be handled at server, to avoid clock freeze in lag situations (check link for explaination: https://support.chess.com/en/articles/8615369-what-is-lag-forgiveness-why-did-the-clocks-suddenly-change).

List of events:
 -> 'connection' - Initialize chess board, set players colors, initialize and set pieces.
 -> 'isInCheck' - Checks if king is attacked and gets all possible moves to block the attack, including, ally piece captures / ally piece path blocks / kings legal moves.
 -> 'getPossibleInterferences' - Get list of possible moves to block check.
 -> 'checkMated' - Marks king as check mated.
 -> 'makeMove' - Perform move from list of legal moves returned from selectPiece event.
 -> 'interfereWithCheck' - Perform the move to block check.
 -> 'getLegalMoves' - Fetch legal moves of selected piece.
 -> 'gameOver' - Marks game as completed and performs closing actions.
 -> 'isDraw' - Handles all types of draws, 50 move rule / 3 peat repetition / stalemates / draw by agreement.
 -> 'response' - A server side event sent to the browser, it contains response data and the initial event type.
 
 Flow of events:
                                    Client                                                          <->                                             Server

    Button Click                                                                                    -> 
                                                                                                    <- Create Websocket, send 'connection' event with ChessGame details (board, players, pieces)
    If first move is not done by both players, send 'abortGame' event                               ->
                                                                                                    <- Close Websocket connection, send 'response' event with game over details.
    Repeat on every move:
        Get current player send 'isInCheck' event                                                   -> 
                                                                                                    <- Check if player is in check, return boolean value in 'response' event along with initial event name
        
        ^ If in check, send 'getPossibleInterferences' event                                        -> 
                                                                                                    <- Return list of non-pinned / non-captured possible moves to block check, send 'response' event along with initial event name
        
        ^^ If no list returned, send 'getLegalMoves' event for king                                 ->
                                                                                                    <- Return kings legal moves, send 'response' event along with initial event name
        ^^^ If no king legal moves, send 'checkMated' event                                         ->
                                                                                                    <- Close Websocket connection, send 'response' event with game over details
        ^^^ If king legal moves, wait for player to perform move

        ^^^^ Player makes move, send 'makeMove' event with from and to position along with moveType ->
                                                                                                    <- Perform move, send 'response' event with success or failed status, along with initial event name
        
        ^^ If list returned, wait for player to perform move
        
        ^^^ Player performs move, send 'interfereWithCheck' event                                   ->            
                                                                                                    <- Perform move, send 'response' event with success or failed status, along with initial event name
        
        ^ If not in check, wait for player to click on piece

        ^^ Player clicks on piece, send 'getLegalMoves' event                                       ->
                                                                                                    <- Check if piece being moved is pinned to king or captured, return 'response' event with no legal moves along with initial event name
        ^^^ If no legal moves, do nothing and wait for player to make move 
        ^^^ If legal moves, wait for player to make move.

        ^^^^ Player makes move, send 'makeMove' event with from and to position along with moveType ->
                                                                                                    <- Perform move, send 'response' event with success or failed status, along with initial event name
        Send 'nextMove' event to get next player data                                               ->
                                                                                                    <- Return next players data, send 'playerUpdated' event with next player data.
            
    Note: If time runs out, 'gameOver' event will be sent from client to server and server will close the websocket and update the game status.
